# ADR-001 — First-run secrets contract

- **Status:** accepted (2026-04-26)
- **Owners:** Nova (backend), Orion (security)
- **Unblocks roadmap:** #1 boot graceful, #10 SSO + per-tenant rate limit
- **Closes audit weaknesses:** §1.6 #1 (`auth.rs:367`), #2 (`crypto.rs:43`), #3 (`server.rs:825`), #4 (`state.rs:669`)

## Context

`nexus-server` panics on first boot in four places when the operator hasn't pre-populated env vars:

| panic | file:line | trigger |
|---|---|---|
| missing JWT secret | `crates/nexus-http/src/security/auth.rs:367` | `NEXUS_JWT_SECRET` unset |
| missing encryption key | `crates/nexus-store/src/crypto.rs:43` | `NEXUS_ENCRYPTION_KEY` unset and no on-disk key |
| empty CORS origins | `crates/nexus-http/src/server.rs:825` | `NEXUS_ALLOWED_ORIGINS` unset in release |
| `secrets.toml` write failure | `crates/nexus-http/src/state.rs:669` | read-only filesystem |

This is the single biggest barrier to the §2.4 wedge demo and to pattern §2.2 #1–2 (one-line install, <10s wow). A `curl | sh` install MUST yield a usable server with zero env vars on the developer's laptop, and MUST fail closed only when the operator explicitly opts into production mode.

## Decision

1. **One canonical secrets file** at `${NEXUS_DATA_DIR:-~/.nexus}/secrets.toml`, mode `0600`, owned by the running user. Schema:

   ```toml
   # Auto-generated by nexus-server first boot. Rotate before production.
   schema_version = 1
   created_at = "2026-04-26T12:34:56Z"
   created_by = "nexus-server v0.x.y dev-mode"

   [jwt]
   # HS256 secret, 32 bytes hex.
   hs256 = "…"

   [encryption]
   # 32-byte AES-GCM key, base64.
   data_key = "…"

   [cors]
   # Dev-mode default. Empty in production unless explicitly listed.
   allowed_origins = ["http://localhost:3000", "http://127.0.0.1:3000"]
   ```

2. **Resolution order at boot** for every secret:
   1. Process env var (`NEXUS_JWT_SECRET`, `NEXUS_ENCRYPTION_KEY`, `NEXUS_ALLOWED_ORIGINS`).
   2. `secrets.toml`.
   3. **Auto-generate** (only if `NEXUS_PRODUCTION != "1"`), persist to `secrets.toml`, log a single WARN line:
      `secrets: generated dev-mode <field>; rotate before production. See docs/adr/001-first-run-secrets.md`.
   4. **Fail closed with structured error** (not `panic!`) — `tracing::error!` + return `Err` from boot. Process exits with code 78 (`EX_CONFIG`) and a remediation message naming the missing field.

3. **Production gate.** Setting `NEXUS_PRODUCTION=1` flips behaviour:
   - Step 3 (auto-generate) is **disabled**.
   - Empty CORS origins → fail closed.
   - `secrets.toml` is read-only-checked; if generated dev secrets are detected (`created_by` contains `dev-mode`), boot fails with a clear message.
   - The frontend Settings UI shows a red "production mode" banner; API keys still come from Settings UI per the existing project memory rule.

4. **Replace, do not parallel-path.** The four `panic!` sites listed above are deleted. There is no `legacy_get_jwt_secret` left for "compat".

5. **Rotation hooks.** `nexus-server rotate-secrets [--field jwt|encryption|all]` CLI subcommand re-generates the targeted field, re-encrypts data-key-protected blobs, and invalidates active JWTs by versioning `[jwt].kid`. JWT verification accepts the previous `kid` for a 24-hour grace window.

6. **What `secrets.toml` does NOT hold.** LLM provider API keys (OpenAI / Anthropic) stay in the Settings UI per existing user memory (`feedback_api_keys.md`). Stripe / Mailgun / S3 credentials stay in env or vault. `secrets.toml` is **only** the platform's own keypairs.

## Consequences

**Positive**
- `curl | sh && nexus-server` boots cleanly on a blank machine; the wedge demo runs.
- Single audit point for platform-internal secrets — one file, one mode, one log line.
- Production deployments still fail closed; nothing is silently weakened.
- `rotate-secrets` becomes a real ops verb instead of "delete the file and pray".

**Negative**
- Dev secrets on disk are a footgun if a laptop is shared or pushed to a docker image without scrubbing. Mitigated by the WARN log on generation and the `dev-mode` marker that production-mode boot rejects.
- Adds a tiny TOML parser dependency (`toml` crate, already in tree).

**Neutral**
- Increases the surface that needs documentation in `docs/` (Phase 5 #8). One cookbook recipe: "preparing for production".

## Alternatives considered

- **Keep panicking, document loudly.** Rejected: the `<10s` wow moment is the wedge; one panic kills it. Three years of OSS adoption data say new users do not read warnings before they `Ctrl-C`.
- **Push everything into env vars only.** Rejected: docker-compose, systemd units, dev laptops, and CI all want different defaults. A file with env override is the union, not the intersection.
- **Use OS keychain (Keychain / DPAPI / libsecret).** Rejected for v1: triples platform complexity, breaks headless containers. Revisit if/when a desktop installer ships.
- **Generate secrets only in debug builds (`#[cfg(debug_assertions)]`).** Rejected: same release binary should run dev and prod; cfg gating diverges them.

## Acceptance test

```bash
rm -rf /tmp/nexus-test && NEXUS_DATA_DIR=/tmp/nexus-test nexus-server &
sleep 2
curl -fsS http://localhost:8080/health   # 200
test -f /tmp/nexus-test/secrets.toml     # exists, mode 600
NEXUS_PRODUCTION=1 NEXUS_DATA_DIR=/tmp/nexus-test nexus-server   # exits 78 with remediation
```
